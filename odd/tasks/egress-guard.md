# Worker egress guard: never scrape PJUD from the office IP
The office fixed IP 186.10.251.189 was blocked by PJUD (28/10 to 06/11) because the station scraped from the office wifi (install day, then Windows auto-joined the office wifi mid-cycle). PJUD has just unblocked it. The station's run-worker.ps1 only checks at startup that PJUD ACCEPTS the login, so now that the office IP is accepted again a cable or a manual wifi change would let the worker scrape from it and get it blocked again.

## Specs
- S1. New setting `FORBIDDEN_EGRESS_IPS: str = "186.10.251.189"` in app/config.py (comma-separated; blank entries ignored; empty string = guard off, exactly today's behaviour). New module `app/services/egress_guard.py` with a pure, injectable core: `current_egress_ip(fetchers=..., timeout=10) -> str | None` asks HTTPS IP echo services in order (https://api.ipify.org, then https://ifconfig.me/ip), returns the first valid IPv4/IPv6 string, None when all fail; and `egress_allowed() -> tuple[bool, str | None, str]` returning (allowed, ip, reason).
- S2. FAIL CLOSED: when the guard is on and the egress IP cannot be determined, scraping is NOT allowed (reason "unknown"). If the internet is down, scraping would fail anyway; never risk the office IP.
- S3. Where: before each lawyer's sync in the scheduler loop (app/workers/sync_scheduler.py; find the per-lawyer call) the worker calls `egress_allowed()`. If not allowed: it does NOT log in to PJUD for that lawyer, records nothing as a completed sync for that lawyer (no misleading sync_history row; if the code always writes one, write status "partial" with error_message "Red no permitida: <ip or desconocida>"), waits (sleep with the existing scheduler pacing, at least 5 minutes) and re-checks before the next attempt. It must never spin in a tight loop.
- S4. Long per-lawyer phases: the detail loop of one lawyer can run up to ~55 min (sync_service.py, DETAIL_BATCH_MAX_SECONDS). Inside that loop, re-check at most every 5 minutes (cache the result for 5 min, monotonic clock, injectable). If it becomes forbidden, stop the lawyer cleanly, the same way the existing preventive rotation stops it (status partial), with error_message "Red no permitida: <ip>". No PJUD request may be made after the forbidden result is known.
- S5. Alert: on the first forbidden/unknown result after an allowed state, send ONE Telegram message through the existing Telegram notifier used for scraping-health alerts (find it; never log the token): "El worker se detuvo: está saliendo a internet por una red no permitida (IP <ip>). No consultará el PJUD hasta volver a una red permitida." For "unknown" use "No se pudo verificar la IP de salida; el worker espera antes de consultar el PJUD." Do not repeat the alert more than once per hour while the state persists; send "El worker volvió a una red permitida (IP <ip>)." once when it recovers. Log every decision at INFO/WARNING with the IP (IPs are not secrets).
- S6. Strict TDD, tests first, RED seen (tests/services/test_egress_guard.py and a scheduler/sync test): parsing of the setting (blank, spaces, several IPs), current_egress_ip fallback order and invalid responses, fail closed on unknown, forbidden IP blocks the lawyer with no PJUD call (spy the PJUD/login entry point), allowed IP proceeds unchanged, empty setting = no lookup at all, the 5-minute cache inside the detail loop and the clean stop there, alert once + once-per-hour + recovery message. No real network in tests. Existing tests keep passing.
- S7. Out of scope: run-worker.ps1 (PowerShell, the parent handles it), the VM, data changes.
