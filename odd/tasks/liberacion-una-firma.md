# Case release (liberación): one signature, out of the semáforo, visible to everyone involved
Backend half. Frontend half: segal-deudores-web odd/tasks/liberacion-una-firma-ui.md (same contract, S1-S5 below).

## Specs
- S1. Releasing takes the case OUT of the semáforo. `POST /liberaciones` accepts `target_semaforo: "gris"` (new value meaning "Liberada") in addition to the current rojo/amarillo/verde (kept for compatibility; the new UI sends only "gris"). `motivo` becomes REQUIRED, stripped, 1-500 chars (400 otherwise, message "Indica el motivo de la liberación."). On apply with "gris": `case.semaforo_override = "gris"` and `case.semaforo = "gris"` (existing override columns; `semaforo_override_by` = the approver's name).
- S2. ONE signature applies it. `POST /liberaciones/{id}/aprobar` by an `admin` OR an `auditor` (existing `_OVERSIGHT_ROLES`) records the sign-off in that role's slot (as today) and applies the release immediately (`estado = "aplicado"`, `aplicado_at`). The second slot is no longer required. Reject unchanged (either role, optional motivo). Lawyers still get 403 on approve/reject. Lock the request row on approve and reject (`with_for_update()`) so two concurrent approvals cannot both apply; a request that is no longer `pendiente` returns 409 as today.
- S3. Durability: an applied release holds until the court dictates something NEW. `DeadlineEngine._apply_semaforo_override` (app/services/deadline_engine.py ~1315) currently clears the override when `case.last_movement_at > semaforo_override_at` (any movement, including the firm's own escritos, so a scrape can undo a release right away). Change: clear it only when a court act (reuse `_is_court_act` from app/services/poder_deadline.py, ignoring `[Nulo]`) has a `movement_date` whose DAY is strictly after the DAY of `semaforo_override_at`. Escritos never clear it. When it is cleared, the case is recomputed normally (as today). Keep the medida prejudicial and non-civil behaviour unchanged.
- S4. Everyone involved can see the request. `GET /cases/{case_id}` (`CaseDetailResponse`, additive, next to `stage_dates`/`window_resolutions`) gets `liberacion: Optional[LiberacionSummary] = None`: the most recent liberación request of the case (any estado), shape `{ id: int, estado: "pendiente"|"aplicado"|"rechazado", target_semaforo: str, motivo: str|null, requested_by_name: str|null, created_at: ISO datetime, approved_by_name: str|null (auditor or dirección name, whichever signed), aplicado_at: ISO|null, rechazado_by_name: str|null, rechazo_motivo: str|null, vigente: bool }`. `vigente` = estado aplicado AND the case's `semaforo_override` is still set (so the UI can tell "Liberada" from an expired release). One extra query at most.
- S5. The pending list for approvers already exists (`GET /liberaciones?estado=pendiente`, `GET /liberaciones/pendientes/count`, admin/auditor). Each list item must include the case `rol`, `tribunal` name and assigned lawyer name (add them if missing) so the Centro operativo card can render without one request per row.
- S6. Strict TDD, tests first, RED seen. Extend tests/api/v1/test_liberaciones.py: gris accepted, motivo required (empty/blank -> 400 with the message), one approval by admin applies, one approval by auditor applies, lawyer 403, second approve after applied -> 409, reject still works; override kept after an escrito dated after the release, kept after a court act dated the same day, cleared after a court act dated a later day, `[Nulo]` ignored; case detail `liberacion` (none, pendiente, aplicado+vigente, aplicado+expired -> vigente false, rechazado); list items carry rol/tribunal/abogado. Existing tests that asserted the two-signature rule are updated to the new rule (report which).
- S7. Out of scope: e-mail/Telegram notifications (production gates e-mail), frontend, data migrations, ownership check on create.
