# Activity audit: who saw and did what in the system, visible to admins
Backend half. Frontend half: segal-deudores-web odd/tasks/activity-audit-ui.md (same contract, S5-S6).

## Specs
- S1. New table `activity_events` (model app/models/activity_event.py, exported in app/models/__init__.py so tests' create_all sees it; alembic `076_activity_events.py`, down_revision "075"; SQLite-compatible types, JSON not JSONB). Columns: id, created_at (UTC, server default, indexed), lawyer_id (nullable FK lawyers.id), actor_name (snapshot, nullable), actor_role (nullable), kind (`view` | `action` | `login` | `login_failed`), method (nullable), route (route TEMPLATE, e.g. `/api/v1/cases/{case_id}`, or the frontend path for views), path (actual path, no query string), status_code (nullable int), case_id (nullable int, indexed), target (nullable str: the main path param value), ip (nullable), user_agent (nullable, trimmed to 255), identifier (nullable: only for login_failed, the submitted email/RUT, never anything else). Index (lawyer_id, created_at). The existing unused `audit_logs` table is NOT touched.
- S2. NEVER store request or response bodies, query strings, headers other than User-Agent, tokens, passwords or keys. The only free-form inputs stored are: the route template, the path, the frontend path for views, and the login identifier.
- S3. Actions: an HTTP middleware in app/main.py (after CORS) records every POST/PUT/PATCH/DELETE under `/api/v1` AFTER the response, with route template (`request.scope["route"].path`, falling back to the path), status code, target (first path param value) and case_id (when the path param is named case_id, or the route is /cases/{id}...; derive generically from path params named `case_id`, or `id` under `/api/v1/cases/`). User from the Bearer token via `decode_access_token` (sub = rut or numeric id) resolved to the Lawyer row (id, name, role) with its OWN SessionLocal (not the request's get_db), so 401/403 responses are recorded too (lawyer_id null when the token is missing/invalid). Excluded: `/api/v1/pjud/ingest/*`, `/api/v1/activity/*` (S4/S5 write their own rows), health endpoints, and every path outside `/api/v1` (sysgal, redaccion, presentacion API-key paths). Recording is best effort: any exception is logged at WARNING and swallowed; the response is never delayed by more than the insert and never fails because of the audit. Must work in tests (tests/conftest.py overrides get_db; make the middleware's session factory overridable so tests point it at the test DB).
- S4. Logins: `POST /auth/web-login`, `/auth/login`, `/auth/login/clave-unica` record kind `login` (success, with the lawyer) or `login_failed` (401/403, with `identifier` = the submitted email/RUT only, trimmed to 120 chars, nothing else from the body). These come from the same middleware (it may read ONLY the identifier field from the JSON/form body of those three routes; if that is not cleanly possible, record login_failed without identifier and report it). Also set `lawyers.last_login_at` on a successful web-login (today it is only set for PJUD/Clave Única logins).
- S5. Views: `POST /api/v1/activity/views` (any authenticated user) body `{ path: str (max 200, must start with "/"), case_id?: int }` -> 204. Records kind `view` with route = path. Dedupe: the same user + same path within 30 seconds records nothing (204 anyway). Unauthenticated -> 401.
- S6. Read API, admin only (`require_admin`; others 403):
  - `GET /api/v1/activity?lawyer_id&kind&desde=YYYY-MM-DD&hasta=YYYY-MM-DD&rol=<ROL text>&page=1&per_page=50 (max 100)` -> `{ items: [{ id, created_at (ISO UTC), lawyer_id, actor_name, actor_role, kind, method, route, path, status_code, case_id, rol (case ROL joined, nullable), target, label, ip }], total, page, pages }`, newest first. `desde/hasta` are Chile-local days (America/Santiago) inclusive. `rol` filters by the case ROL (case-insensitive contains).
  - `label`: a short Spanish description computed server-side from (kind, method, route) with a small mapping for the main actions (e.g. "Inició sesión", "Intento de inicio de sesión fallido", "Vio la causa", "Vio <pantalla>" for known frontend paths such as /causas, /plazos, /hitos, /agenda, /productividad, "Creó un hito", "Editó un hito", "Solicitó una liberación", "Aprobó una liberación", "Rechazó una liberación", "Marcó un plazo como cumplido", "Exportó", "Cambió su contraseña"); unknown -> "<METHOD> <route>". Read the routers to build the mapping for the real routes (report the list).
  - `GET /api/v1/activity/summary?dia=YYYY-MM-DD` (Chile day, default today) -> per person active that day: `{ lawyer_id, actor_name, actor_role, first_at, last_at, views, actions, cases_viewed (distinct case_id) }`, sorted by last_at desc.
- S7. Strict TDD, tests first, RED seen (tests/api/v1/test_activity*.py): an action is recorded with template/status/user/case_id; a 403/401 is recorded; bodies never stored (POST a password to /auth/web-login and to a credentials route and assert the password text appears in no column); login and login_failed with identifier; last_login_at on web-login; excluded paths not recorded; audit failure does not break the request (make the insert raise); views endpoint + 30 s dedupe + 401; admin-only reads (lawyer 403); filters (lawyer, kind, days in Chile time across UTC midnight, rol) and pagination; summary counts. Existing tests keep passing untouched.
- S8. Out of scope: retention/purge (follow-up), frontend, e-mail, the old audit_logs table.
