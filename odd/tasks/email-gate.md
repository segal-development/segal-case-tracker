# One gate for every outgoing e-mail
Stop all e-mails except "Plazos fatales del estudio" to Carla Lavin. There is no switch today: e-mails leave from four places.

## Specs
- S1. Request (L1, L2, verbatim): "que pare los envios de correos para todos excepto a Carla Lavin y que solamente le siga llegando el de los movimientos" and, choosing from the table of e-mail types, "Solo el envio de Plazos fatales del estudio | Carla". Result: ONLY the e-mail "Plazos fatales del estudio" (daily_agenda.py, subject "Plazos fatales del estudio — {dia} ({total})", sent to Carla) keeps going. Everything else stops: the movements digest, the plazo/semaforo alerts, the daily agenda to each lawyer, the notificacion/escrito/exhorto/deadline e-mails, the supervisor credential alert and the scraping-down alert.
- S2. Mechanism, configurable WITHOUT a deploy (two settings read from the environment, in app/config.py): `EMAIL_ALLOWED_KINDS: str = ""` and `EMAIL_ALLOWED_RECIPIENTS: str = ""`, both comma-separated. Empty = no restriction (today's behaviour, so tests and dev are unchanged). Kinds, as constants in a new module `app/services/email_gate.py`: `movimientos`, `plazos`, `plazos_verde`, `agenda`, `plazos_fatales_estudio`, `notificaciones` (the per-alert e-mail, notificacion/escrito/exhorto/deadline), `supervisor`, `scraping`. Function `email_allowed(kind, *addresses) -> bool`: true iff (kinds setting is empty or the kind is in it) AND (recipients setting is empty or EVERY address, To and Cc, is in it); case-insensitive, trimmed. Log at INFO (not ERROR) what was suppressed: kind and the recipient count, never the body.
- S3. Apply the gate at EVERY real send, at the point where the message goes out, not in each caller: `NotificationService._deliver` in app/services/notification_service.py (add a required `kind` parameter; every caller passes its own kind: movements digest `movimientos`, plazo e-mail `plazos`, plazo-verde digest `plazos_verde`, per-alert `send_email_alert` and the notificacion/escrito/exhorto/deadline paths `notificaciones`), `_send_email` in app/services/daily_agenda.py (add `kind`: the lawyer agenda is `agenda`, Carla's urgent digest is `plazos_fatales_estudio`), `_send_smtp_sync` in app/services/supervisor_alert_service.py (`supervisor`) and `_enviar_email` in app/services/scraping_health.py (`scraping`). Read each one first.
- S4. A suppressed e-mail must NOT be recorded as sent: `alert.email_sent` / `email_sent_at` stay as they were, and callers that return True on success return False (nothing raises, nothing logs as an error). Digest buckets that are flushed and dropped are simply dropped (a digest is never resent: that is the intended effect). `send_webhook` and Telegram are NOT e-mail: untouched.
- S5. Tests first (strict TDD, RED seen): `email_allowed` (empty settings allow everything; kinds only; recipients only; both; Cc counts; case and spaces; unknown kind blocked when a list is set); then one test per send point proving that with `EMAIL_ALLOWED_KINDS=plazos_fatales_estudio` and `EMAIL_ALLOWED_RECIPIENTS=carla@segal.cl` nothing is handed to SMTP for the other kinds, that Carla's urgent digest IS still sent, and that a suppressed per-alert e-mail leaves `email_sent` False. Mock `smtplib.SMTP` or the existing transport seam the current tests use. Existing tests keep passing untouched (default settings are empty).
- S6. Out of scope: configuring the VM, Telegram, webhooks, the content of any e-mail, scheduling.
