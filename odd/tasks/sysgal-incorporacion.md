# Sysgal → automatic incorporation of the firm's causas not yet visible in our system
Every causa the firm takes in Sysgal must end up followed by our system automatically, even while the lawyer's patrocinio/poder is not yet accredited in PJUD (so it is not in the lawyer's "Mis causas", which is what our scraper reads). Staged; each stage is its own PR. Nothing users see changes until the last stage.

## Specs
- S1. Request (Marcelo, 2026-11-10, verbatim): "Es que no se si eso sea bueno.. la idea es hacerlo automatico , para eso se construyo el sistema... como lo podemos hacerr de otra manera?" Approved plan ("dale"): daily Sysgal sync; queue of active Sysgal causas with a valid ROL that we do not have; the station fetches them from PJUD by ROL (public Consulta Unificada, `consulta_by_rol` in app/scrapper/pjud/civil.py) and incorporates them under the Sysgal lawyer, marked "Patrocinio pendiente"; when the lawyer later accredits patrocinio the Mis-causas sync recognizes the same causa (no duplicate) and clears the mark.
- S2. Pace (Marcelo approved the recommendation): first 3 days 100 per day, spread ~10 per hour; then up to 300 per day if PJUD shows no rejections or empty details. Priority: ROL year 2026, then 2025, then older; within a year, most recently updated in Sysgal first. Automatic brake: on PJUD rejection / login failure / repeated empty detail the incorporation stops and alerts via Telegram (existing notifier). Must not consume the per-account ~60 min detail budget of the normal cycles.
- S3. Evidence (production, 2026-11-10): Sysgal active causas with valid ROL 8,095; matched 4,333; not matched 3,762 = ~345 cuadernos (fixed in #446), ~448 same ROL only in another court, ~2,969 not in our DB at all (2024-2026, civil courts, all lawyers). Example confirmed by Eduardo Venegas: C-6628-2026, 4º Juzgado Civil de Santiago: in Sysgal as his; in PJUD visible but patrocinio/poder not accredited.
- S4 (stage 1). Daily automatic Sysgal sync: run `sync_sysgal_causas(db, client)` (incremental) once a day in the process that can reach Sysgal (only the QA VM IP 34.121.223.42 is whitelisted; the station egress is NOT, Sysgal answers 403). Gate with a new setting `SYSGAL_CAUSAS_SYNC_ENABLED: bool = False` (enabled only on the VM). Find where `sync_sysgal_estados` is scheduled (app/workers/sync_scheduler.py ~1067) and which deployment runs it; hook the causas sync the same way, failure-isolated (an exception logs and never breaks the cycle), at most once per calendar day (Chile). Report in the logs the stats dict.
- S5 (stage 1). Incorporation queue: new table `sysgal_incorporaciones` (migration 081): id, sysgal_causa_id (FK sysgal_causas, unique, ON DELETE CASCADE), estado ('pendiente' | 'incorporada' | 'no_visible' | 'sin_corte' | 'error' | 'descartada'), prioridad (int; lower = first), intentos int default 0, ultimo_error nullable (short, never a body), proximo_intento_at nullable, corte (int nullable, PJUD corte code), court_id nullable FK courts, case_id nullable FK cases (ON DELETE SET NULL), created_at, updated_at. Add the cases FK table to case_merge's CHILD_TABLES_WITH_CASE_ID.
- S6 (stage 1). `encolar_incorporaciones(db)` (called right after each Sysgal sync): enqueue every Sysgal causa with estado 'activa', valid ROL (`^[A-Z]-\d+-\d{4}$` after normalize_rol), not eliminada, case_id null and match_method not 'ambigua', and not already queued. Resolve the court: Sysgal tribunal name → our `courts` row by the same normalized tribunal key the matcher uses; set court_id and corte (`Court.pjud_corte`); unresolvable → estado 'sin_corte'. Priority = rank by (ROL year desc, sysgal_updated_at desc). When a queued causa later gets matched (case_id set by a later sync), mark it 'incorporada' with that case_id. Idempotent.
- S7 (stage 1). Admin read-only endpoint `GET /api/v1/sysgal/incorporaciones/resumen`: counts by estado, by ROL year and by lawyer (Sysgal responsible mapped to our lawyer name when mapped), plus the first 20 pending in priority order (ROL, tribunal, lawyer, year). No writes.
- S10 (stage 2). The station worker consumes `sysgal_incorporaciones` (estado 'pendiente', ordered by prioridad) and fetches each causa from PJUD with `consulta_by_rol(session, rol, corte, tribunal="0")` (app/scrapper/pjud/civil.py), reusing the SAME session acquisition the repo already uses for consulta_by_rol elsewhere (find the existing callers; never a lawyer's per-account Mis-causas session budget). Runs inside the station's sync scheduler between lawyer units, never inside a lawyer's 55-min detail batch, and behind the existing egress guard (no PJUD request from a forbidden or unknown IP).
- S11 (stage 2). Pace controlled FROM THE SERVER, not the station env (the station is not reachable to edit): a DB-stored setting `sysgal_incorporacion_por_dia` (int, default 0 = OFF) and `sysgal_incorporacion_por_hora` (int, default 10), read by the station each time; reuse an existing key/value settings table if the repo has one, otherwise a small new one (next migration after the current head). Admin endpoints `GET/PUT /api/v1/sysgal/incorporaciones/ritmo` (admin only) to read/set them. Count consumed per Chile calendar day and per clock hour from the queue rows' own timestamps (no in-memory counters), so restarts do not reset the quota.
- S12 (stage 2). Outcome per item (in one transaction per item): found in PJUD → create the Case through the existing ingest/upsert path used for PJUD case details (court = the queue row's court_id, rol, plaintiff/defendant, procedure, movements, documents metadata as the normal sync stores them), with `Case.lawyer_id` = our lawyer mapped from the Sysgal responsible (sysgal_usuarios.lawyer_id; unmapped → estado 'error' with ultimo_error 'abogado sin relacionar', no case created), and a new boolean `cases.patrocinio_pendiente = True`; set queue estado 'incorporada' + case_id and the sysgal_causas.case_id/match_method ('pjud_rol'). If a case with the same rol+court already exists (any lawyer/procedure Principal) do NOT create another: link it ('incorporada', match) instead. Not found in the consulta (reserved or absent) → 'no_visible'. Any other failure → intentos+1, ultimo_error (short, never a body), proximo_intento_at with backoff (1h, 6h, 24h), 'error' after 3 attempts. After creating a case, run the normal deadline recompute for it.
- S13 (stage 2). The incorporated case must be VISIBLE to its lawyer and alert him: verify (with tests) that `resolve_case_scope`/`case_ids_for_abogado` include a case whose only link to the lawyer is `Case.lawyer_id` (no firm litigante in PJUD), and that `resolve_case_alert_recipients` falls back to that lawyer; if not, make the minimal change so they do, without changing behaviour for cases that have firm litigantes.
- S14 (stage 2). Brake: if within one run there are 3 consecutive PJUD failures of the same kind (session expired/redirect to login, empty detail modal, HTTP error) or any login rejection, stop the incorporation for the rest of the Chile day, record why, and send ONE Telegram alert through the existing notifier ("Incorporación desde Sysgal detenida: <motivo>. Se reintenta mañana."). Never log credentials or page bodies.
- S15 (stage 2). Strict TDD, tests first, RED seen; PJUD fully mocked (fake consulta_by_rol returning a parsed detail / None / raising). Cover: quota per day/hour from DB (0 = nothing), priority order, egress guard respected, found → case created with lawyer_id + patrocinio_pendiente + queue/link updated, existing rol+court → linked not duplicated, unmapped lawyer → error without case, not found → no_visible, retries/backoff/error after 3, brake after 3 consecutive failures + single Telegram, scope and alerts include the incorporated case, admin-only ritmo endpoints. Migration for `cases.patrocinio_pendiente` (+ settings table if needed): single head.
- S16 (stage 2 fix). An incorporated case must carry the full plaintiff and defendant. Observed in prod 2026-11-11 (first 5 incorporations): C-4950-2026 and C-6219-2026 got plaintiff "BANCO DE CRÉDITO E INVERSI" and an EMPTY defendant, because the consulta-by-ROL caratulado comes truncated and `_persist_found` only splits `detail.case.caratulado`. Fix: take plaintiff/defendant from the detail's litigantes (DTE./DDO. or the equivalent roles the parser already exposes) when available, falling back to the caratulado split only when there are none; never store a truncated name when a complete one is available. Repair the already-incorporated cases with an empty defendant or a plaintiff that is a prefix of the litigante name, using data already stored in our DB (case litigantes) when present — no new PJUD request; if our DB has nothing better, leave them. Tests first (RED seen) with a fixture reproducing the truncated caratulado.
- S17 (stage 3). No duplicate when the causa shows up in Mis causas: when a lawyer's normal Mis-causas sync ingests a causa whose rol + court (+ Principal or empty cuaderno, the same identity `_existing_case` uses) matches an existing case with `patrocinio_pendiente = true`, it must update THAT case (never create a second Case row) and keep `patrocinio_pendiente` until a firm abogado litigante is stored (see L7); from then on its owner follows the normal rules (PJUD litigantes, manual override). Movements already stored are not duplicated (the normal movement dedup applies). Find how the normal ingest upserts cases (app/services/sync_service.py, the unique identity from migration 072) and prove with tests that no duplicate is created; add the flag clearing there. Also clear the flag when a later consulta/detail sync of that case shows a firm abogado litigante (the patrocinio is now accredited). Provide `contar_duplicados_incorporadas(db)` (read-only) returning any pairs of cases with the same identity where one is patrocinio_pendiente, for a prod check.
- S18 (stage 3). API: `patrocinio_pendiente: bool` in the case list items and the case detail of `/api/v1/cases`; list filter `patrocinio_pendiente=true|false`; and its count in the existing Causas summary/counters response used for the filter chips (follow how other chip counts are returned), respecting the caller's case scope.
- S19 (stage 3). Front (segal-deudores-web): a badge "Patrocinio pendiente" in the Causas list row and in the case detail header, with tooltip "Incorporada desde Sysgal: el patrocinio aún no está acreditado en el PJUD."; a filter chip "Patrocinio pendiente (N)" in Causas next to the existing chips, wired to `?patrocinio_pendiente=true` (URL param like the other chips) and to the count of S18; the CSV export gets a "Patrocinio pendiente" column (Sí/No). Visible to every role that sees the case.
- S20 (stage 3). Strict TDD both repos (RED seen). Backend: Mis-causas ingest of an incorporated causa updates the same case and clears the flag (no new Case, movements not duplicated); firm litigante appearing clears it; non-incorporated cases unchanged; filter and count respect scope; duplicates check function. Front: badge in row and detail, chip count and URL param, CSV column; `tsc -b`, lint, vitest; Chrome visual check.
- S8. Stage 2 (later PR): the station worker consumes the queue with the S2 pace and brake via `consulta_by_rol`, creates the Case (+ movements/documents through the existing ingest path), owner = Sysgal lawyer, flag `patrocinio_pendiente`. Stage 3: dedup/merge when the causa appears in Mis causas, clear the flag; UI badge. Not in stage 1.
