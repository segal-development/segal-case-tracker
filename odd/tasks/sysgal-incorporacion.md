# Sysgal → automatic incorporation of the firm's causas not yet visible in our system
Every causa the firm takes in Sysgal must end up followed by our system automatically, even while the lawyer's patrocinio/poder is not yet accredited in PJUD (so it is not in the lawyer's "Mis causas", which is what our scraper reads). Staged; each stage is its own PR. Nothing users see changes until the last stage.

## Specs
- S1. Request (Marcelo, 2026-11-10, verbatim): "Es que no se si eso sea bueno.. la idea es hacerlo automatico , para eso se construyo el sistema... como lo podemos hacerr de otra manera?" Approved plan ("dale"): daily Sysgal sync; queue of active Sysgal causas with a valid ROL that we do not have; the station fetches them from PJUD by ROL (public Consulta Unificada, `consulta_by_rol` in app/scrapper/pjud/civil.py) and incorporates them under the Sysgal lawyer, marked "Patrocinio pendiente"; when the lawyer later accredits patrocinio the Mis-causas sync recognizes the same causa (no duplicate) and clears the mark.
- S2. Pace (Marcelo approved the recommendation): first 3 days 100 per day, spread ~10 per hour; then up to 300 per day if PJUD shows no rejections or empty details. Priority: ROL year 2026, then 2025, then older; within a year, most recently updated in Sysgal first. Automatic brake: on PJUD rejection / login failure / repeated empty detail the incorporation stops and alerts via Telegram (existing notifier). Must not consume the per-account ~60 min detail budget of the normal cycles.
- S3. Evidence (production, 2026-11-10): Sysgal active causas with valid ROL 8,095; matched 4,333; not matched 3,762 = ~345 cuadernos (fixed in #446), ~448 same ROL only in another court, ~2,969 not in our DB at all (2024-2026, civil courts, all lawyers). Example confirmed by Eduardo Venegas: C-6628-2026, 4º Juzgado Civil de Santiago: in Sysgal as his; in PJUD visible but patrocinio/poder not accredited.
- S4 (stage 1). Daily automatic Sysgal sync: run `sync_sysgal_causas(db, client)` (incremental) once a day in the process that can reach Sysgal (only the QA VM IP 34.121.223.42 is whitelisted; the station egress is NOT, Sysgal answers 403). Gate with a new setting `SYSGAL_CAUSAS_SYNC_ENABLED: bool = False` (enabled only on the VM). Find where `sync_sysgal_estados` is scheduled (app/workers/sync_scheduler.py ~1067) and which deployment runs it; hook the causas sync the same way, failure-isolated (an exception logs and never breaks the cycle), at most once per calendar day (Chile). Report in the logs the stats dict.
- S5 (stage 1). Incorporation queue: new table `sysgal_incorporaciones` (migration 081): id, sysgal_causa_id (FK sysgal_causas, unique, ON DELETE CASCADE), estado ('pendiente' | 'incorporada' | 'no_visible' | 'sin_corte' | 'error' | 'descartada'), prioridad (int; lower = first), intentos int default 0, ultimo_error nullable (short, never a body), proximo_intento_at nullable, corte (int nullable, PJUD corte code), court_id nullable FK courts, case_id nullable FK cases (ON DELETE SET NULL), created_at, updated_at. Add the cases FK table to case_merge's CHILD_TABLES_WITH_CASE_ID.
- S6 (stage 1). `encolar_incorporaciones(db)` (called right after each Sysgal sync): enqueue every Sysgal causa with estado 'activa', valid ROL (`^[A-Z]-\d+-\d{4}$` after normalize_rol), not eliminada, case_id null and match_method not 'ambigua', and not already queued. Resolve the court: Sysgal tribunal name → our `courts` row by the same normalized tribunal key the matcher uses; set court_id and corte (`Court.pjud_corte`); unresolvable → estado 'sin_corte'. Priority = rank by (ROL year desc, sysgal_updated_at desc). When a queued causa later gets matched (case_id set by a later sync), mark it 'incorporada' with that case_id. Idempotent.
- S7 (stage 1). Admin read-only endpoint `GET /api/v1/sysgal/incorporaciones/resumen`: counts by estado, by ROL year and by lawyer (Sysgal responsible mapped to our lawyer name when mapped), plus the first 20 pending in priority order (ROL, tribunal, lawyer, year). No writes.
- S8. Stage 2 (later PR): the station worker consumes the queue with the S2 pace and brake via `consulta_by_rol`, creates the Case (+ movements/documents through the existing ingest path), owner = Sysgal lawyer, flag `patrocinio_pendiente`. Stage 3: dedup/merge when the causa appears in Mis causas, clear the flag; UI badge. Not in stage 1.
- S9. Out of scope for stage 1: any PJUD request, ownership switch, UI, e-mail.
