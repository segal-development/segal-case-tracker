# Traspaso de cartera: move every case of a departing lawyer, smartly, with history and undo
Three work units: A alerts follow the assigned lawyer, B backend plan/apply/revert, C admin wizard (segal-deudores-web).

## Specs
- S1. Request (Marcelo, 2026-11-06, verbatim): "hay unaa abogada que yaa no trabaja con nosotros y todas sus causas deben pasar a otro abogado.. como podemos hacer una automatizacion para que Carla lo pueda hacer dentro del sistema pero de manera mas inteligente y automatizada?" Approved proposal: 3-step wizard (choose the departing lawyer → automatic preview with a smart distribution → confirm), history of who owned each case so it can be undone, optional block of the departing account, and alerts/semáforo going to the ASSIGNED lawyer. "si vamos con todo".
- S2 (unit A). Alerts follow the assignment. Today `resolve_case_alert_recipients` (app/services/lawyer_roster.py) uses only CaseLitigante and `effective_lawyer_id` only as fallback (sync_service.py ~1213, semaforo_alerts.py ~129), so a case reassigned with `cases.assigned_lawyer_id` keeps alerting the PJUD litigante. New rule: when a case has `assigned_lawyer_id` (override) and that lawyer is active, the case's lawyer recipients are that lawyer instead of the litigante abogados (the override REPLACES, the same precedence `_abogado_litigantes_by_case` already uses). Without override: unchanged. Apply it to every path that picks lawyer recipients for a case: new-movement alerts, plazo/semáforo alerts (incl. `_extra_lawyers`), and any other caller of the recipient resolver (enumerate them). Non-lawyer recipients (admins/digests) unchanged. Tests: override → only the assigned lawyer gets movement and plazo alerts; no override → today's recipients; inactive override target → falls back to today's rule.
- S3 (unit B). `POST /api/v1/asignacion/traspaso/plan` (admin only) body `{ origen_lawyer_id: int, destino_lawyer_ids?: int[] (empty/absent = every eligible lawyer), destino_unico_id?: int (send everything to one lawyer) }` → dry run, writes nothing:
  - Cases of the origin: non-archived cases whose RESOLVED owner (`resolved_owner_by_case`: override > litigante) is the origin.
  - Summary: `total`, `por_nivel` (matriz levels), `por_semaforo`, `plazos_proximos` (active plazos due within 10 calendar days), `liberaciones_pendientes`, and `solo_cuenta_origen`: cases whose ONLY PJUD sighting (`case_lawyer_source` / `Case.lawyer_id` provenance used by the sync rotation) is the origin's account — they stop refreshing when the origin is blocked until another lawyer is patrocinante in PJUD.
  - `propuesta`: one item per case `{ case_id, rol, tribunal, matriz, semaforo, proximo_plazo (date|null), destino_lawyer_id, destino_nombre, advertencia (null | "nivel no coincide" | "sin matriz") , solo_cuenta_origen: bool }`.
  - Smart distribution (deterministic): eligible destinations = active firm lawyers except the origin (filtered by `destino_lawyer_ids` when given). Order cases by urgency: rojo, then amarillo, then the rest; within each, nearest plazo first, then case id. Each case goes to an eligible lawyer whose level matches the case matriz (reuse NIVELES_REQUERIDOS / the asignación engine's level rule) choosing the minimum of (urgent cases received in this plan when the case is urgent, then current resolved load + received in this plan), ties by lowest lawyer id. No level match → minimum load among all eligible + advertencia "nivel no coincide"; no matriz/provisional → minimum load + "sin matriz". `destino_unico_id` → everything to that lawyer (warnings still computed).
  - `carga`: per destination `{ lawyer_id, nombre, nivel, carga_actual, recibe, recibe_urgentes, carga_final }`.
  - 422 when the origin does not exist, there are no eligible destinations, or a destination is not an active firm lawyer.
- S4 (unit B). `POST /api/v1/asignacion/traspaso/aplicar` (admin) body `{ origen_lawyer_id, asignaciones: [{ case_id, destino_lawyer_id }], bloquear_origen: bool }`: validates every case still belongs to the origin (409 listing the ones that changed) and every destination is an active firm lawyer (422); in ONE transaction writes the override through the ORM (`assigned_lawyer_id`, `assigned_at`, `assigned_by_rut`, `assigned_motivo` = "Traspaso de cartera de <nombre origen>") so the 60 s scope cache is invalidated, and writes one history row per case into a new table `case_assignment_history` (migration 078 after 077: id, batch_id (uuid str), case_id, from_lawyer_id (resolved owner before), prev_assigned_lawyer_id, prev_assigned_at, prev_assigned_by_rut, prev_assigned_motivo, to_lawyer_id, motivo, created_by_rut, created_at, reverted_at). If `bloquear_origen`: block the origin exactly like the existing account block (reuse the same code path). Returns `{ batch_id, aplicadas, bloqueada }`. Existing `POST /asignacion/reasignar` also writes history rows (its own batch_id) so manual moves keep the previous owner too.
  - `POST /api/v1/asignacion/traspaso/{batch_id}/revertir` (admin): restores each case's previous override columns exactly as stored (including NULL = no override), marks rows `reverted_at`; skips cases whose current override is no longer the one this batch wrote (report them). Does NOT unblock the account. `GET /api/v1/asignacion/traspaso` lists batches (batch_id, created_at, created_by, origen, count, reverted).
- S5 (unit B). Tests first (RED seen): ownership selection (override and litigante), smart distribution (urgent first and spread, level match, no-level and sin-matriz warnings, ties, destino filter, destino_unico), solo_cuenta_origen, plan writes nothing, apply (override + history + cache invalidated + motivo + bloquear), 409 when a case changed owner between plan and apply, 422s, revert (restores NULL and previous override, skips changed cases), reasignar writes history, admin-only (lawyer/auditor 403). Use the ORM (no bulk query.update). Existing tests keep passing.
- S6 (unit C, frontend). Admin screen "Traspaso de cartera" (route /traspaso, sidebar Sistema, and a "Traspasar cartera" action on each person in Cuentas del estudio that opens it preselected). Step 1 choose the departing lawyer (and optionally restrict destinations or pick one destination). Step 2 preview from the plan endpoint: summary cards (total, por nivel, por semáforo, plazos próximos, liberaciones pendientes), the per-destination load table, the warning block "N causas solo se actualizan con su cuenta PJUD: hay que tramitar el patrocinio" with a CSV download (ROL, tribunal, destino), and the case list paginated by 20 with each proposed destination editable via a select (edits are sent in `asignaciones`). Step 3 confirm dialog (count, destinations, checkbox "Bloquear la cuenta de <nombre>"), apply, then a success panel with the batch and a "Revertir traspaso" action; a history list of past batches with revert. Loading and error states everywhere. Tests first; tsc -b, eslint, vitest, build.
- S7. Out of scope: PJUD patrocinio filings (the system only lists the cases), e-mail (gated), hitos already credited (stay with whoever earned them), cartera snapshots already frozen.
