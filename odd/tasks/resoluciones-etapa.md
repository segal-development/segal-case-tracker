# Case detail: the court resolutions of the excepciones window
Rodrigo Campos (case C-8962-2026): a Mero tramite that states no plazo because it needs a prior gestion. "La idea es que el sistema siga indicando las resoluciones que se vayan dictando. Mientras no aparezca la resolucion para acreditar poder, nunca se llegara al traslado de las excepciones."

## Specs
- S1. `GET /cases/{case_id}` (get_case in app/api/v1/cases.py; it already loads every movement and already returns `stage_dates`) gets a new optional field `window_resolutions: list[WindowResolution] = []` on `CaseDetailResponse`. Additive, default `[]`.
- S2. When to fill it: only while the case sits in the window, i.e. `case.procedural_state in ("excepciones", "notificado")` AND it is not a medida prejudicial (reuse `is_medida_prejudicial(case.procedure)` as `_stage_dates` does) AND an `Opone excepciones` escrito exists (reuse `is_excepciones_filing` in app/services/poder_deadline.py). Otherwise `[]`.
- S3. Which movements: the court acts (`_is_court_act`: procedure not `Escrito`; skip `[Nulo]`) dated on or after the FIRST `Opone excepciones` escrito, up to and including the first `Opone excepciones-Traslado` resolution when there is one (use `_is_traslado_resolution`), oldest first, capped to the LAST 8. The `Opone excepciones` escrito itself and `Acredita Poder`-style compliance movements are NOT listed as resolutions; compliance is reported as the outcome of the resolution it fulfils (S4).
- S4. Shape of each item (put the logic in a PURE function in app/services/poder_deadline.py, `window_resolutions(movements, today) -> list[dict]`, so it is unit-testable and shares the rule with the plazo): `{ "date": "YYYY-MM-DD", "description": str (as stored, stripped), "requires_action": bool, "status": str, "due_date": "YYYY-MM-DD" | null, "resolved_on": "YYYY-MM-DD" | null, "resolved_by": str | null }`.
  - `requires_action` = the movement is `Previo a proveer` (`is_previo_a_proveer`) or an extended trigger wording (`is_extended_trigger`, Mero tramite / Apercibimiento poder), WITHOUT the cutoff and WITHOUT the "no later stage" and ownership checks: this is a display of what the court dictated, not the plazo engine.
  - `status`, for `requires_action` items: `"cumplida"` when a compliance movement (`is_compliance_movement` or `is_extended_compliance_movement`) is dated strictly after it (`resolved_on`/`resolved_by` = that movement's date and description); else `"avanzo"` when a traslado resolution is dated strictly after it (the court moved on; `resolved_on` = its date); else `"vencida"` when `add_business_days(date, 3) < today`; else `"pendiente"`. `due_date` = `add_business_days(date, 3)` (business days count Saturday; use the existing helper exactly as the plazo does). For non-action items: `status = "informativa"`, `due_date = null`.
  - Two requires_action resolutions: each is evaluated against compliance dated strictly after ITSELF (an `Acredita Poder` before the second one does not fulfil it).
- S5. Strict TDD, tests first, RED seen: unit tests of `window_resolutions` with the shapes of Rodrigo's real cases (C-10700 shape: Opone excepciones 21/09, Mero tramite 01/10, Acredita Poder 05/10 -> `cumplida`; C-8962 shape: Mero tramite with no compliance, still within 3 days -> `pendiente`, past 3 days -> `vencida`; C-1319 shape: court goes straight to the traslado -> no requires_action item; a later `Opone excepciones-Traslado` after an unfulfilled Mero tramite -> `avanzo`; `[Nulo]` ignored; cap of 8; informative items such as `Confiere traslado de incidente`; two triggers; unsorted input), and endpoint tests (field present in the window, `[]` outside it, `[]` for a medida prejudicial, `[]` when there is no Opone excepciones, scope unchanged, no extra query: assert the query count does not grow). Existing tests keep passing untouched.
- S6. Out of scope: any frontend change, the semaforo and the plazo engine (they must not change), the cutoff setting, data changes, e-mails.
