# Sysgal as the primary source
Sysgal becomes the primary source of each causa's responsible lawyer and of the cartera intake; PJUD (Case Tracker's own scraping) becomes the secondary source.
Backend: /Users/marcelo/Projects/segal-case-tracker. Frontend: /Users/marcelo/Projects/segal-deudores-web.

## Specs
- S1. Ownership precedence (agreed in September, now decided): (1) manual override `cases.assigned_lawyer_id` (traspaso de cartera) always wins; (2) the responsible lawyer in Sysgal: the case is linked to an ACTIVE, non-eliminated `sysgal_causas` row (`case_id`, its own link; if several, the most recently updated, then highest id) whose `abogado_sysgal_id` maps to a lawyer via `sysgal_usuarios.lawyer_id`, and that lawyer is active; (3) otherwise the current PJUD rule (abogado-of-record litigantes / Case.lawyer_id as today). Unmapped or inactive Sysgal lawyer → fall through to (3). Terminated/eliminated Sysgal rows never decide ownership. Measured 2026-11-13: of 4,949 linked cases with a mapped Sysgal lawyer, 2,202 keep their owner and 2,747 change (Eduardo +490, Luis +487, Gonzalo +426, Melissa +225, Rodrigo +213, Ricardo +204, Pablo +199…).
- S2. ONE place decides ownership: the shared resolver in app/services/lawyer_roster.py (`_abogado_litigantes_by_case` / `resolved_owner_by_case` and everything derived from it: `case_ids_for_abogado`, `resolve_case_scope`, firm dashboards, risk board, `/matriz/por-abogado`, asignación) AND the alert recipients (`resolve_case_alert_recipients`, `acting_lawyer_is_case_abogado`, deadline alert emission) must follow the same precedence, so a lawyer sees exactly the cases whose alerts he receives. The case-scope cache must be invalidated when a sysgal_causas link / abogado / estado changes (same mechanism as `_CASE_SCOPE_COLUMNS`, or an explicit invalidation after the Sysgal sync). Preloaded in bulk (no per-case query).
- S3. Kill switch: a server-side setting `sysgal_es_fuente_duenio` (int in `goals`, 1 = on) read with a short cache; 0 → exactly today's behaviour (PJUD only). Default after deploy: 0 (off); turned on by the parent after the prod dry-run report is approved. A read-only report function `reporte_cambio_duenio(db) -> {lawyer: {gana, pierde}}` and a script `scripts/reporte_duenio_sysgal.py` print, per lawyer, how many cases they gain/lose if the switch is turned on (without turning it on).
- S4. Sin ROL causas (Marcelo, 2026-11-13: "Sí, como causas 'Sin ROL'"): Sysgal causas without a valid ROL (rol "0", empty, not matching the ROL pattern) become cases in our system marked `sin_rol = true`, with Sysgal data only (cliente RUT, tribunal text if any, abogado responsible = Sysgal lawyer, etapa/trámite for the matriz), no PJUD data, no movements/plazos, semáforo neutral ("Sin ROL" instead of a color), visible to their Sysgal lawyer and in the firm totals, excluded from PJUD scraping; when Sysgal later sends a valid ROL for that causa, the case gets the ROL and joins the normal incorporation/linking flow without creating a duplicate. Scope of this slice: SPEC ONLY — implemented in a later task after S1-S3 are live (T3).
- S5. Strict TDD (RED seen) for S1-S3: precedence (override > Sysgal active mapped lawyer > PJUD), unmapped/inactive/terminated fall through, several Sysgal rows pick the latest, scope == alert recipients for every case in the fixture, kill switch 0 is byte-identical to main (differential over the existing roster/scope/alert tests), cache invalidation after a Sysgal link change, report counts, no N+1.
